RustMonitor 硬件管理三域隔离
host 降级为 L1 后，对硬件的访问会 VM-Exit 到 monitor 吗 —— 答案在"信任域"与"页表挖洞"
核心结论
L1 绝大多数硬件访问（PIO / MMIO / 外部中断 / CR）直通、零 VM-Exit；隔离不靠"每次拦截仲裁"，而靠 SLAT 把 monitor 内存与 EPC 映射成空页 —— "你根本映射不到"，仅 CPUID / hypercall / NMI / Enclave 事件四类会 exit
Ⅰ 普通世界（L1）
Normal World · Untrusted
Linux 内核 / App→ 直通 →真实硬件
  • PIO / MMIO / 绝大多数 MSR / 外部中断全直通，无 VM-Exit
  • CR3 切换零 exit（CR3 exiting 显式禁用），进程切换不受影响
  • CPUID 被仿真伪装：隐藏 VMX/SVM 位、宣告 hypervisor 存在
  • 异常 / #PF 直达 L1 自己 IDT，Linux 缺页处理完全无感
零 VM-Exit非信任
Ⅱ Monitor（TCB）
RustMonitor · VMX Root
VMCALL→ VM-Exit →hypercall 分发
  • 仅 CPUID / hypercall / NMI / Enclave 事件 四类 exit，拦截面极窄
  • 三套页表：GPM(EPT/NPT) · HVM(自身) · DMA(IOMMU)
  • EPCM / EDMM 管理 Enclave 生命周期与 EPC 页回收
  • monitor 内存 + EPC 在 GPM 与 DMA 中映射空页 / 不映射
窄拦截面RoT = TPM
Ⅲ Enclave（S-world）
GU-Enclave · Ring3
EENTER→ 切页表 →独立 NPT + GPT
  • EFER.SCE 关闭：Enclave 内禁止 syscall
  • 全异常拦截（bitmap 全 1）→ 任何事件 AEX 弹回普通世界
  • 内存对 L1 与 DMA 设备结构性不可见（机密性主防线）
  • 与普通世界共享同一 vCPU，切换仅页表指针级开销
机密性AEX 兜底
一句话：隔离强度来自"映射不到"，而非"每次访问都仲裁"图 1 · 整体架构
Hypercall 调用链七步往返
L1 与 monitor 的唯一上行控制通道 —— 从 VMCALL 陷入到读回返回值
核心结论
编码即特权级（code bit31：0=Supervisor 驱动级 / 1=User enclave 级）+ 状态双重校验（CpuState）+ 指针必经 L1 页表翻译 —— monitor 从不直接信任 L1 传来的地址；enclave 无法调用创建/销毁自己的 Supervisor 级 hypercall
Ⅰ 发起 · 陷入
Trap In
App / 驱动 VMCALL→ VM-Exit →arch_entry
  • 寄存器约定：RAX=code、RDI/RSI=参数
  • Intel VMCALL / AMD VMMCALL 触发硬件陷入
  • 切到 monitor 私有栈 → vmexit_handler
ring0 / ring3 均可发起
Ⅱ 校验 · 分发
Validate & Dispatch
from_regs→ 校验 →handler
  • 特权级：CS.DPL vs code bit31，不符注入 #UD
  • 状态：validate_state 查 CpuState，不符注入 #UD
  • 指针：GVA 经 L1 CR3 页表 → GPA（marshalling），绝不直接解引用
bit31 = 特权级CpuState 校验

Trap Out
set_return_val→ VMEntry →L1 续跑
  • 结果写回 RAX；HvError 注入 #GP、EnclaveError 返回码
  • advance_rip 跳过 VMCALL 指令本身
  • L1 从下一条指令继续，读 RAX 得返回值 / 错误码
RAX = 结果40+ handler

系统调用路径三情形谱系
L1 降级后 syscall 会不会 VM-Exit —— 三种情形的"对手"不同
核心结论
普通世界 syscall 零 exit 直通；Enclave 内 SYSCALL 因 EFER.SCE=0 触发 #UD → AEX 被禁；正确 I/O 只能 EEXIT 由非信任运行时代理 + 共享内存编组 —— Enclave 与内核无直接接口
Ⅰ 普通世界直通
Normal World Passthrough
SYSCALL→ LSTAR →Linux 内核
  • EFER.SCE=1，syscall 机制启用
  • VMX 不拦截 SYSCALL 指令（无对应 exit）
  • monitor 完全不参与，Linux 原生全速处理
零 VM-Exit全速
Ⅱ Enclave 内禁用
Enclave Syscall Blocked
SYSCALL→ #UD →AEX 弹回
  • EENTER 已从 EFER 减去 SCE（禁 syscall）
  • SCE=0 时 SYSCALL 在硬件层触发 #UD
  • 全异常拦截 → 存 SSA → 向 AEP 注入 #UD，弹回普通世界
禁直接 syscall#UD → AEX
Ⅲ 正确 I/O（OCALL）
Controlled Exit
EEXIT→ 代理 syscall →ERESUME
  • syscall 由非信任运行时在普通世界代做
  • 数据经 SharedMemoryAdd 白名单 共享内存编组跨界
  • 受控出站：把"直接接口"收窄为"经常校验的间接接口"
受控出站共享内存编组
一句话：Enclave 的 I/O 攻击面 = 一块经 monitor 校验的共享内存，而非整个内核 ABI图 3 · Syscall 路径
Enclave 世界切换四路转换
共享同一 vCPU 的"视图寄存器原子替换" —— 不是 VM 切换，是页表指针级开销
核心结论
EENTER / ERESUME 仅 HvEnabled 发起、EEXIT / EACCEPT 仅 EnclaveRunning 发起（validate_state 强制）；AEX 是唯一被动转换 —— 存现场到 SSA 后把寄存器摆成"刚从 EnclaveEnter 返回"，交由普通世界 AEP 接管
EENTER
0x8000_0000 · Enter
HvEnabled→EnclaveRunning
  • 存 normal_state（RSP/RBP → SSA.ursp/urbp）
  • 切 NPT+GPT root、IDTR=0、清 SCE
主动进入
EEXIT
0x8000_0001 · Exit
EnclaveRunning→HvEnabled
  • 恢复 normal_world_state（页表/IDT/EFER）
